The Lying Packet

Every machine on a local network answers one question on the honour system — “which of you owns this address?” This project puts a program in the middle of the network that remembers the answers, and notices when one of them changes.

The problem

A local network runs entirely on trust

Two machines on the same network don’t reach each other by IP address. They reach each other by hardware address — the MAC burned into the network card. Something has to translate between the two, and that something is ARP.

ARP works by shouting. A host broadcasts “who has 192.168.1.4?” to everyone on the wire and waits. Whoever replies is believed. There is no signature on the reply, no authority to check it against, and no rule that says a later answer can’t overwrite an earlier one. First answer wins — until a second answer arrives, and then that one wins.

In plain terms

Picture a mailroom where anyone can walk in and announce “I’m the accounting department now — send their post to me.” Nobody asks for ID. Everyone crosses out the old entry and writes down the new one. That is genuinely how ARP works, and it has worked that way since 1982.

The attack, concretely

In this lab, host h1 runs ettercap. It sends h3 a forged reply claiming to be h4, and sends h4 a forged reply claiming to be h3. Both victims update their notes. From that moment every packet between them lands on h1 first, gets read, and is passed along.

Nothing appears to break. The ping still returns. The transfer still completes. That silence is the point — it is why the technique is called a man in the middle.

Why SDN makes it catchable

Separating the thinking from the forwarding

An ordinary switch decides where packets go using logic baked into its firmware. You can configure that switch. You cannot teach it something new.

Software-defined networking splits the box in two. The switch keeps only a flow table — a list of rules that say match this, do that. All the actual decisions move into a separate program, the controller, which runs on an ordinary computer in a language you can edit.

When a packet arrives that no rule covers, the switch doesn’t guess. It wraps the packet up and sends it to the controller as a packet_in message — it asks. The controller replies with what to do, and usually installs a rule so it won’t be asked again.

That question is the opening. Write one rule saying every ARP packet must be asked about, and you get to inspect every ARP message on the network before it is delivered. Which is exactly what this project does.

The idea

You can’t verify a packet. You can verify a history.

The reasoning behind this project runs in four steps, and the third is where it turns.

One. An ARP message carries no proof of anything. There is no field to check, no key to verify against. Examining a single packet in isolation is hopeless — a forged reply is byte-for-byte as valid as a real one.

Two. But nothing says you have to judge a packet in isolation. You can judge it against everything you have already seen.

Three. A real machine’s identity is a triple that does not change during a session: this MAC address, holding this IP, arriving on this physical switch port. Records that stay together.

Four. So record the triple the first time you see it, and hold every sender to it afterwards. A forged ARP reply has to lie about at least one leg — that is what forging means here — so it cannot match.

In plain terms

It is not cryptography and it isn’t clever. It’s the doorman who has worked the building for years: he can’t inspect your ID, but he knows that the person who has walked in through the west door every morning claiming apartment 1 has just walked in through the same door claiming apartment 3. That’s enough.

Architecture

Four hosts, one switch, one program

The whole system runs on a single Linux machine. Mininet builds a real network out of kernel namespaces and virtual interfaces; the controller talks to it over a genuine OpenFlow socket. Nothing here is simulated at the protocol level.

The controller keeps two dictionaries, both keyed by switch ID so the design would survive more than one switch:

mac_to_port — the ordinary learning-switch table. Answers where do I send traffic for this MAC?

mac_to_ip — the security table. Answers what is this MAC allowed to claim? This one is the project.

The decision pipeline

What happens to one packet

Every packet the switch cannot handle alone lands in a single Python function and walks through the same sequence. This one is an ordered process, so the order matters.

  1. Discard link-layer discovery traffic

    LLDP frames are how controllers map topology. They are not user traffic and are dropped before anything else runs.

  2. Learn the source

    Record which port this MAC arrived on, so future traffic to it can be sent directly instead of flooded. Standard learning-switch behaviour, unchanged from the Ryu example this project started from.

  3. Is it ARP?

    Anything else skips the check entirely and goes to normal forwarding. Only ARP carries an address claim, so only ARP needs validating.

  4. Check the binding — or create it

    If this MAC has never been seen, store its IP and port and let the packet through: first sighting is always trusted. If it has been seen, compare both the IP and the ingress port against the stored pair.

  5. On a mismatch, block the port

    Log the attacker’s MAC and the IP it tried to claim, push a drop rule for that switch port, and return without forwarding the packet.

  6. Otherwise, forward — and install a shortcut

    For IPv4 traffic with a known destination, the controller also installs a flow rule so subsequent packets in that conversation never come back to it. ARP deliberately gets no such shortcut — that is what keeps the check running.

What lives in the switch

Four rules, read top down

An OpenFlow switch checks its table in priority order and stops at the first match. These four rules, and the order they sit in, are the entire enforcement side of the project.

101drop

in_port = <attacker> → (no actions)

Installed only when an attack is detected. OpenFlow has no explicit “drop” instruction — you match the traffic and give it an empty action list, and the packet simply goes nowhere. Sitting above the ARP rule, it silences that port completely rather than just for ARP.

100watch

eth_type = 0x0806 (ARP) → send to controller

Installed the moment the switch connects. This is the load-bearing rule: it forces every single ARP packet up to the controller instead of letting the switch forward it at line rate. Without it the detection would see nothing after the first few packets.

1fast path

in_port + eth_src + eth_dst → output to port

Added on demand, per conversation, with a 10-second idle timeout. This is what keeps the controller from becoming a bottleneck: ordinary traffic gets a rule after its first packet and stops asking. Short-lived on purpose, so the network re-learns rather than drifting stale.

0fallback

match anything → send to controller

The table-miss rule. Anything no other rule covers becomes a question for the controller. Every OpenFlow application installs one; without it, unmatched packets are dropped silently and the controller never learns anything.

What the block actually does

The drop rule carries idle_timeout=300, which means the switch deletes it after five minutes with no matching traffic. The block is therefore self-healing: an attacker who goes quiet gets their port back automatically. Whether that is a feature or a gap depends on what you want from it — see what it doesn’t catch.

Running the lab

Three terminals

Everything runs on one Linux host — Mininet needs kernel namespaces, so macOS and Windows need a VM. The two feature flags at the top of app.py let you watch the attack succeed first, then switch on the defence.

  1. Install the attacker’s tool

    $ sudo apt install ettercap-text-only

  2. Start the controller

    Terminal one. It stays in the foreground and logs every ARP packet it sees.

    $ ryu-manager app.py

  3. Build the network

    Terminal two. This creates s1 and the four hosts, connects to the controller on localhost, and drops you at the Mininet prompt.

    $ sudo python3 topology.py

  4. Generate honest traffic

    At the Mininet prompt, keep h3 talking to h4 so there is something worth intercepting.

    mininet> h3 ping 192.168.1.4

  5. Attack from h1

    Terminal three, inside h1. This is the line that forges both replies and starts relaying.

    mininet> xterm h1 h1# ettercap -T -i h1-eth1 -w test1.pcap -M ARP /192.168.1.3// /192.168.1.4//

  6. Watch the three modes

    Edit the two flags at the top of app.py and re-run to see each stage.

    # attack succeeds silently ARP_POSION_DETECTION = 0 ARP_POSION_MITIGATION = 0 # attack is logged, but still works ARP_POSION_DETECTION = 1 ARP_POSION_MITIGATION = 0 # attack is logged and the port goes dark ARP_POSION_DETECTION = 1 ARP_POSION_MITIGATION = 1

With mitigation on, the controller prints the offending MAC and the address it tried to claim, and h1’s port stops passing traffic. The capture written to test.pcap opens in Wireshark, where the duplicate-address warning makes the forged replies easy to spot.

What it doesn’t catch

The honest edges

The design is deliberately small, and small designs have visible edges. These are worth knowing before anyone treats it as a defence rather than a demonstration.

MAC spoofing walks past it

The table is keyed by MAC address. An attacker who forges the source MAC as well as the IP simply creates a fresh, unseen entry — and first sighting is always trusted. Catching that needs a second key, such as a static port-to-address binding configured up front.

Whoever speaks first, wins

Bindings are created from whatever the controller happens to see first. An attacker present at boot poisons the table itself, and the legitimate host is then the one flagged and blocked. The check is only as trustworthy as the network’s first thirty seconds.

The block is blunt

Mitigation kills the entire switch port, not just the offending traffic. On this four-host lab that is exactly one attacker. On a port with a downstream switch behind it, it is everyone.

And it expires quietly

The drop rule’s five-minute idle timeout removes the block with no notification and no record. An attacker who pauses is readmitted.

The MAC is learned regardless

The forwarding table is updated before the ARP check runs, so a rejected packet still leaves its source MAC in mac_to_port. Harmless here, but it means the two tables can disagree.

if buffer_id:

A real bug. OpenFlow buffer ID 0 is valid, and 0 is falsy in Python — so that one flow gets installed on the wrong branch. It should read if buffer_id is not None:. Rare enough to be invisible in a lab, which is exactly why it survives.

About the repository name

The project is published as “Interference Mitigation Using Software-Defined Network Based Next-Generation Networks” — a title from the academic framing around it. The code is narrower and more concrete than that suggests: it detects and blocks ARP poisoning on an SDN. This page describes the code.
